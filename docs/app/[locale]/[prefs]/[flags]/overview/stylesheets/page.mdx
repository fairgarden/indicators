# Stylesheets

A site with many heavy pages cannot afford a copy of each per preference.
It still has preferences, and most of them are things a stylesheet can
express — a theme above all. So an indicator can be expressed through a
stylesheet instead of a path segment:

```ts
export const indicators = createIndicators({
  locales: ['en', 'fr'],
  defaultLocale: 'en',
  segments: ['locale'],
  prefs: { theme: { values: ['light', 'dark'], stylesheet: '/theme.css' } },
})
```

The route tree is then `app/[locale]/…`, every page has one copy per
locale, and the theme is a tiny stylesheet the browser asks for on every
page.

A site in one language drops the locale as well:

```ts
export const indicators = createIndicators({
  segments: [],
  prefs: { theme: { values: ['light', 'dark'], stylesheet: '/theme.css' } },
})
```

That is a plain `app/…` tree with nothing dynamic in it, no rewrite on any
page, and one preference served as CSS. [Hard flags](/overview/hard-flags)
still work there, at the front of the path.

## How it is served

Nothing runs for it. `/theme.css` is rewritten, by the same cookie match
that would otherwise build a path segment, to one of three static files in
`public/`, named after it and the value:

```
public/theme.light.css      cookie theme=light
public/theme.dark.css       cookie theme=dark
public/theme.default.css    no cookie, or any other value
```

and answered with `Cache-Control: private, no-cache, stale-if-error`. So
the browser keeps its copy but asks every time, which is a 304 while the
cookie has not changed and a new file once it has; no cache in front keeps
it; and a stale copy stands in when the server cannot answer, since it is
only ever the wrong theme. The files are a line each, so a fresh copy is
barely heavier than the 304. The plugin says so at build time when one of
them is missing.

The layout links to it, after the app's own styles so that what it sets
wins:

```tsx
import { Stylesheets } from '@fairgarden/indicators'

<head>
  <Stylesheets indicators={indicators} mount={mountPrefix('@fairgarden/id')} />
</head>
```

A flag works the same way, from a header: `memory: { header:
'device-memory', values: { low: '0\\.25|0\\.5|1|2' }, stylesheet:
'/memory.css' }` serves `/memory.low.css` to a device with 2 GB of memory
or less, which can turn off blur and parallax. No media query says how much
memory a device has. That hint is one a browser sends only once the site
asks for it with `Accept-CH`, which the plugin does on every page, and a
stylesheet has it from the first page. See [Indicators](/overview/indicators) for
which hints need asking for, and which browsers send them. Both stylesheets and the
files they are rewritten to are excluded from the locale rewrite.

The match happens in the routing layer, so it can use what a script in the
page never could:

```ts
flags: {
  // added by the edge network, never seen by the browser
  region: { header: 'x-vercel-ip-country', values: { eu: 'AT|BE|DE|FR|IT|NL' }, stylesheet: '/region.css' },
  // an HttpOnly cookie, hidden from scripts; any value will do
  session: { cookie: 'session', values: { in: '.+' }, stylesheet: '/session.css' },
}
```

A visitor from Germany gets `/region.eu.css`, and one with a session
cookie gets `/session.in.css`. The session match only tests that the cookie
is there, so an expired or forged cookie matches too. That is enough to
decide how a page looks, such as an account menu instead of a sign-in
button, but not anything that needs the session to be valid; the server
still has to check that.

A download page is another case. One static page carries a button for
every platform, and a stylesheet chosen by `User-Agent` hides all but the
visitor's. Every browser names its operating system there, so it works
everywhere, from the first visit. Keeping it out of the path matters: a
flag in the path would make a copy of every page on the site per
platform, for one button. The [download demo](/demos/download) does
this, with the architecture from `Sec-CH-UA-Arch` on top.

## On some pages only

By default the layout links every stylesheet, so every page asks for it.
A stylesheet that one page uses, like the download page's, can be left to
that page:

```ts
flags: {
  os: { header: 'user-agent', values: { mac: '.*Macintosh.*' }, stylesheet: '/platform/os.css', global: false },
}
```

```tsx
// app/[locale]/[prefs]/[flags]/download/page.tsx
<Stylesheets indicators={indicators} only={['os']} />
```

The layout's `<Stylesheets>` then leaves it out, and no other page asks for
it. The page's link carries a React `precedence`, so React puts it in the
`<head>`. It also holds a client-side navigation to the page until the
stylesheet has loaded, so the page never shows a frame without it.

Such a stylesheet is not in the preload header, which lists only what
every page links. A `Link` header that differed from page to page would
not survive two sets of pages overlapping, since Next keeps one value per
header. The plugin still asks for the client hints it reads on every page,
since a browser remembers them for the whole site anyway.

## The round trip, and the preload

This is the tradeoff. The stylesheet blocks rendering and is never fresh,
so even a page the browser has cached in full waits one round trip before
it can render. The answer is a 304 with no body, so that round trip is
short. A page the browser has not cached is not slowed down, because its
stylesheet request goes out alongside the requests that page makes anyway.

To keep the round trip short, every page names the stylesheets every page
links in a `Link` header:

```
Link: </theme.css>; rel=preload; as=style
```

On its own the header gains little. A browser scans HTML for `<link>` tags
as it arrives, before parsing it, and Next sends the `<head>` together
with the response headers, so the request goes out at almost the same
moment either way. On a fast network the 304 is back before the page has
finished parsing, with or without the header. The header pays off when a
CDN turns it into a 103 Early Hints response, which reaches the browser
before the page does. The 304 then overlaps the time the server takes to
answer, and there is little of it left.

The header goes on every page. Here a page is any path that does not start
with an excluded segment (`_next`, `api`, `.well-known`, `exclude`, and
what the plugin found in the app) and whose last segment has no extension.
`/fr/login` and `/` are pages; `/api/users`, `/favicon.ico` and
`/theme.css` are not. `preloadStylesheets: false` in
[`withFairGardenIndicators`](/functions/withFairGardenIndicators) turns it
off.

## What the files say

One declaration is enough when the palette is written for it. With colors
as `light-dark()` pairs, `color-scheme` picks the mode:

```css
/* theme.dark.css */
:root { color-scheme: dark; --theme: dark }
/* theme.light.css */
:root { color-scheme: light; --theme: light }
/* theme.default.css */
:root { color-scheme: light dark; --theme: system }
```

`light dark` follows the OS, so the default costs nothing. The same
declaration on `[data-theme='dark']` serves the sites that keep the theme
in the path, so one palette serves both kinds. A palette split into a light
file and a dark file can instead be switched with a one-line `@import` of
the right one, at the price of a dependent request.

The custom property is for scripts. Nothing has to parse a cookie or guess
the OS setting; the stylesheet that was served is the answer:

```ts
getComputedStyle(document.documentElement).getPropertyValue('--theme')   // 'dark'
getComputedStyle(document.documentElement).colorScheme                    // 'dark'
```

For an indicator a script cannot read, such as a header added by the edge
or an `HttpOnly` cookie, this is the only way to learn which value
matched. It gives away the name of the value, never the cookie:
`session.in.css` can set `--session: in`.

Rendering never waits on a script. The link is ordinary render-blocking
CSS, tiny, and applied before the first paint, so there is no flash of the
wrong theme.

## Changing it

`usePref('theme')` works as for a preference in the path, with two
differences. Setting it writes the cookie and then fetches the stylesheet
again — a fresh `<link>` with a cache-busting query, after the layout's —
so the change shows without a reload, and nothing server-rendered depends
on it, so there is no refresh. And since the value is not in the params,
the hook reads it from the cookie after mounting: it is `undefined` on the
server and on the first render.

## What it changes

A stylesheet indicator is left out of the segment, of
`generateStaticParams`, and of what `read` and `useIndicators` return; it
does not multiply the pages, which is the point. It cannot switch what a
page renders — that is what the [path](/overview/paths) is for — only how
it looks.
